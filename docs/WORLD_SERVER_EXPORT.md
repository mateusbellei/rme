# Procedural server bundles and house ownership

The isolated `--generate-world` exporter can optionally convert residential
construction footprints into real OTBM house tiles and matching `world-houses.xml`
records. This applies to generated templates and fixed-orientation OTBM prefabs.
It does not add house metadata to the editor's World undo transaction.

```powershell
rme --generate-world data/procedural/recipes/example_prefab_town_1098.json data/1098/items_original1098.otb data/1098/items_original1098.xml data/1098/materials.xml build/server-world --data-dir data --town-prefix Frontier --house-prefix Residence --house-rent 250 --no-previews --no-diagnostics --verify | Out-Host
```

Use a new output directory. On Linux, run under Xvfb and omit `| Out-Host`.
The catalog must explicitly assign `role:"residential"` to rentable constructions.
Other roles, streets, plazas and surrounding terrain retain ordinary ownership.
House export requires `--town-prefix` and at least one placed residential template;
an unsatisfied request fails before creating output.

## House records

- `--house-prefix NAME` enables house ownership. IDs start at one and follow the
  deterministic residential placement order. Names append the house ID to the
  prefix. Prefixes allow 1..64 printable UTF-8 bytes, including spaces within a name.
- `--house-rent NUMBER` sets the same nonnegative integer rent for every exported
  house (default zero, maximum 2147483647). It requires `--house-prefix`.
- Every declared occupied footprint cell belongs to its house, across all placed
  floors, including walls, entrances and base courtyards. Upper courtyard voids
  remain unowned. XML `size` follows the native editor's nonblocking tile count;
  the report's `tiles` includes all assigned tiles.
- Each house references the town of its settlement. Its entry/eviction position
  is the physically walkable public cell immediately outside the base entrance.
  No extra terrain or door item is inserted to manufacture a safe exit.
- Existing top-level door items receive unique IDs 1..255 within each house.
  More than 255 doors fails. Prefabs still reject authored server/script metadata;
  these new IDs are assigned only during optional batch export.

Procedural templates can have an open arch instead of a door item. Their house
ownership remains valid, but the exporter reports a warning: lockable entrances
must be authored separately. Exporting ownership does not establish server access
rules, visual correctness or playable housing. Real-client/server QA is pending.
Spawns, NPCs, guildhalls and physical stairs are not generated by this option.

`generation.json` records `housePrefix`, `houseRent` and a `houses` array containing
ID, name, town ID, source building index, entry position, rent, owned tile count,
native size and door count. Without `--house-prefix`, the array is empty and
ordinary OTBM tiles remain unchanged.

`--verify` reopens the written OTBM, requires identical re-encoding, reloads the
written house XML onto the reopened house tiles and compares the native XML
re-export with the original metadata. This includes exits on floor z=0.
The production reader accepts valid exits with zero x, y or z components, rather
than incorrectly treating each zero component as an unset position.

House/town options are batch export settings, not planner settings. To reproduce
the same server bundle from `recipe.json`, pass the same town/house prefix and
rent options again. The plan fingerprint describes geography/constructions and
does not change when optional server ownership is enabled.

## Keeping output small

Two independent options omit authoring diagnostics without changing server data:

| Option | Omitted files |
| --- | --- |
| `--no-previews` | The five preview PNGs per floor |
| `--no-diagnostics` | `plan.json` and uncompressed `plan_z*.ppm` |

Both default to exporting their files for backwards compatibility. Together they
leave OTBM, XML sidecars, `generation.json` and the reproducible `recipe.json`.
`generation.json.diagnosticsExported` reports whether plan diagnostics were written.
`--editable-inputs` remains an independent opt-in and can still write authoring PNGs.
Verification remains enabled when requested; neither option weakens map checks.

Each diagnostic PPM uses three bytes per cell plus a small header. A five-layer
1024x1024 plan therefore writes roughly 15 MiB of PPMs before any PNG or OTBM.
One 2048x2048 layer uses roughly 12 MiB. No duplicate source prefab files are added
to bundles; keep their catalog/assets available for replay.

Build caches and separate review checkouts consume substantially more disk than
the source prefab sample. Reuse configured build directories for incremental
work. CLI regressions use temporary directories which are removed after the run;
manual exported bundles remain until explicitly cleaned. Do not delete a checkout
or its ignored files merely because the associated PR has been merged.

## Validation

The external CLI regression uses the public 10.98 registry and checks generated
and authored houses, residential filtering, town membership, rental XML, native
house tile/door attributes, byte-identical replay, disabled housing, invalid
options and z=0 exit readback. Compact export must retain identical OTBM/XML bytes
while producing fewer disk bytes and no omitted diagnostics/previews.

On 2026-10-18, a Windows x64 Release export of a 2048x2048 surface with the public
10.98 registry/materials passed `--verify`: 4,194,304 tiles, four towns and 52
residential houses. Observed time was 15.09 seconds, peak working set 2682.1 MiB
and compact bundle size 33.43 MiB. These are measurements on one machine, not CI
performance guarantees. This uses the 4,194,304 tile budget exactly: adding populated
cave/upper floors to the full-size surface exceeds that budget. No DAT/SPR or real
game server was used. To reproduce, adapt `example_large_continent_1098.json` to
width/height 2048, `buildingLevels:1`, `caveDepth:0`, then pass the house options,
`--tile-budget 4194304 --no-previews --no-diagnostics --verify`.
